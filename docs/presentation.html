Backup · 1 of 5 · Architecture and technical difficulty

What's actually hard here, engineering-wise?

Two full interview pipelines behind one interface. The default is a single bundled ElevenLabs Conversational AI agent handling speech, reasoning, voice and turn-taking together. Behind a flag is a five-piece pipeline we built ourselves: Deepgram for speech-to-text, Claude for reasoning, ElevenLabs for voice, and a deterministic controller deciding when the interviewer should speak. Both drive the same panel and the same evidence-based reviewer.

Why not just call an LLM on every keystroke or transcript fragment?

The interviewer is gated by interview-stage rules and meaningful-event detection, not a raw event stream. It has to feel like a person deciding when to speak, not a live autocomplete system.

How is the candidate's code actually understood?

Direct extraction from the editor's own state, not OCR or screen-reading. Screen or tab capture exists only as an optional secondary signal, and is off by default in the current pipeline.

Backup · 2 of 5 · Models, data and evaluation

Why ElevenLabs Conversational AI as the default, and not a custom pipeline for everything?

It bundles STT, reasoning, TTS and turn-taking into one low-latency agent, which matters when the whole point is a conversation that feels real-time. The separate-pieces pipeline gives more control, a fuller rubric, tiered hints, but more latency and more moving parts, so we kept it as a fallback rather than the default.

How do you evaluate output quality?

Manual live testing against a real LeetCode-style page and a real microphone, plus targeted regression tests written against bugs we actually hit. There is no formal automated evaluation harness yet. We're saying that plainly rather than overselling it.

Is the code analysis itself AI-generated, or something more reliable?

Deterministic static analysis (Python's own AST) for Python submissions, so complexity and structure observations aren't hallucinated. Other languages currently fall back to LLM-only analysis.

Backup · 3 of 5 · Known limitations

What breaks, or isn't finished?

If the connection drops mid-interview, transcription can currently fail to resume until the client restarts its audio stream. The interview itself keeps running either way. We know the exact fix and haven't shipped it yet.

Is the live rubric you see during the interview fully evidence-based?

In the default pipeline it's a blended live preview, not the fully evidence-linked version. The fallback pipeline has the fuller version, tied directly to transcript and code evidence.

What's the newest, least battle-tested part of the system?

The voice pipeline itself. It's been manually tested end-to-end and tuned once against live feedback, but doesn't yet have the automated test coverage the rest of the codebase has.

Backup · 4 of 5 · Alternatives and differentiation

How is this different from just using ChatGPT's voice mode?

It can't see your code or the problem, and it isn't scoped to behave like an interviewer, so it will just solve the problem for you if asked. Ours reads your actual editor state and is deliberately built to guide rather than solve.

What about Pramp-style peer mock interview platforms?

Those need a second real person, scheduled in advance. This is on demand, on the exact problem you're already solving, with nobody else's calendar involved.

What about just using LeetCode on its own?

LeetCode gives you the problem and a judge for your final answer. It has no one asking why you chose that approach while you're still choosing it.

Backup · 5 of 5 · Feasibility and value

What would it take to make this a real product, not just a hackathon build?

Real per-session cost accounting, since speech-to-text, the LLM and voice are all billed by usage and that isn't tracked yet. Broader static-analysis language support beyond Python. Hardening the auth and persistence path already stood up on the deployed backend. And a proper privacy and consent pass on microphone capture, beyond the capture safeguards already built in.

Who benefits, and roughly how much?

Anyone preparing for a technical interview without a study partner on hand. Instead of scheduling a peer session or paying for a mock interview, they get an on-demand rep for the marginal cost of a few API calls.

Any cost or regulatory concern worth naming?

Mainly usage-based provider costs at scale, and the standard care around recording consent that comes with capturing microphone audio. Nothing exotic, but not free either.
